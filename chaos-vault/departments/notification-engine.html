Notification Engine

Notification lifecycle states and a simple queue manager from Jellycat Tracker. Handles pending, delivered, read, expired, and dismissed transitions. The Pro paywall gate is quarantined.

1 Reconstructed 1 Experimental 1 Quarantined
Provenance
Donor · Jellycat Tracker

Jellycat Tracker sent in-app notifications when watched items changed price, came back in stock, or were removed from listings. Each notification had a lifecycle: it started as pending (queued server-side), became delivered (sent to the client), transitioned to read (user saw it), and eventually expired or was dismissed. A Pro tier gate existed in the original — that logic is quarantined (CV-NOT-003). The lifecycle contract and the queue manager are the portable parts.

Notification Lifecycle States

Reconstructed
State machine5 states with validated transitions. Invalid transitions are rejected, not silently applied.
TTLConfigurable per notification type. Default: 24 hours. Expired notifications are moved to a separate log, not deleted.
PersistenceThis contract describes the state model — storage (DB, localStorage, in-memory) is application-defined.
RiskLow. Pure state machine. No UI dependency.
STATE MACHINE 
// CV-NOT-001 · Notification Lifecycle

const STATES = ['created','pending','delivered','read','dismissed','expired']

const TRANSITIONS = {
  created:   ['pending',   'expired'],
  pending:   ['delivered', 'expired'],
  delivered: ['read',      'expired'],
  read:      ['dismissed', 'expired'],
  dismissed: [],                       // terminal
  expired:   [],                       // terminal
}

function transition(notification, nextState) {
  const allowed = TRANSITIONS[notification.state] ?? []
  if (!allowed.includes(nextState)) {
    throw new Error(
      `Invalid transition: ${notification.state} → ${nextState}`
    )
  }
  return { ...notification, state: nextState, updatedAt: new Date() }
}

// Notification record shape
Notification {
  id:        string
  type:      string             // matches CV-RTE-001 event types
  state:     typeof STATES[number]
  payload:   object
  createdAt: Date
  updatedAt: Date
  expiresAt: Date
  _read:     boolean
}

CV-NOT-002

Notification Queue Manager

Experimental

A simple in-memory queue that prevents notification flooding, enforces per-type rate limits, and coalesces duplicate events before delivery.

Rate limitMax 3 notifications of the same type per 60-second window.
CoalescingIf the same item triggers two price updates within 5 seconds, only the second (most current) is delivered.
RiskMedium. The coalescing window is application-specific and must be tuned per use case. Default values are guesses.
QUEUE MANAGER SKETCH 
// CV-NOT-002 · Notification Queue Manager (experimental)

class NotificationQueue {
  #queue   = []
  #counts  = new Map()          // type → [timestamps]
  #pending = new Map()          // coalescingKey → timer

  enqueue(notification) {
    const { type, coalescingKey } = notification

    // Rate limit check
    const window = 60_000, maxPerWindow = 3
    const now = Date.now()
    const recent = (this.#counts.get(type) ?? []).filter(t => now - t < window)
    if (recent.length >= maxPerWindow) return // silently drop
    this.#counts.set(type, [...recent, now])

    // Coalescing — debounce within 5s by key
    if (coalescingKey) {
      clearTimeout(this.#pending.get(coalescingKey))
      this.#pending.set(coalescingKey, setTimeout(() => {
        this.#deliver(notification)
        this.#pending.delete(coalescingKey)
      }, 5000))
      return
    }

    this.#deliver(notification)
  }

  #deliver(notification) {
    this.#queue.push({ ...notification, state: 'delivered' })
    this.onDeliver?.(notification)
  }
}

The paywall UI existed but the Stripe/RevenueCat wiring was never completed — the gate was a stub that checked a boolean flag with no real payment verification.
